# Disclaimer

## This code was written by an AI

The G-code macros, shell scripts, Python, and documentation in this
repository were generated by Claude (Anthropic) in conversation with the
repository owner. It was not typed out by a human.

## It was tested and reviewed by a human

It is not unreviewed AI output dumped into a repo. Every version was run
on real hardware — an Ender 3 V3 SE driven by Klipper on a Raspberry Pi
Zero 2 W — and the AI's first attempts were wrong in ways that only
showed up on the machine. Among the bugs found and fixed during testing:

- A multi-line `RUN_SHELL_COMMAND` in a Jinja template, which Klipper
  splits into separate commands and rejects as malformed.
- Template placeholders shipped unsubstituted, producing a bare
  `Error running command` with no diagnostic output. `install.sh` now
  fails loudly if any placeholder survives.
- Moonraker contacted over HTTP, which fails when `force_logins` is set.
  Replaced with the unauthenticated unix domain socket.
- The auto-start helper writing its output to `/dev/null`, leaving no way
  to diagnose it. It now logs to `plr/start.log`.
- Two different code paths deriving the state directory independently.
- The hotend heating in parallel with the bed, so it sat molten and
  drooling for the twenty minutes the bed needed. Bed now heats alone first.
- A second `PLR_RESUME` rewriting the output file at the moment Klipper
  opened it. Guarded by an arm lock.

The heating order, purge behaviour, and countdown timing were changed in
response to real print results, not theory.

## What that does and does not buy you

It means the code has been exercised end to end on one machine, and that
its obvious failure modes have been hit and fixed. It does not mean it is
correct. It has been tested on exactly one printer, by one person, over a
short period. There is no test suite, no CI, and no second pair of eyes.

Areas most likely to hold remaining bugs:

- Slicers other than OrcaSlicer/PrusaSlicer. Layer marker detection and
  absolute-E reconstruction are heuristic.
- Printers whose kinematics or bed mesh behave differently from a simple
  cartesian with a single Z leadscrew.
- Multi-extruder, multi-material, or IDEX setups. Untested, likely broken.
- Any config where `SET_KINEMATIC_POSITION` interacts with other Z
  transforms (`z_tilt`, `quad_gantry_level`, skew correction).

## The physical risk is real

This software is not a text generator whose worst outcome is a bad
paragraph. Recovery ends with a hot nozzle descending onto an existing
part at a Z height read from a file that was written during a power
failure. If that value is wrong, the nozzle collides with your print, your
bed, or your probe.

Before running a recovery file, open it and read the preamble. Watch the
first Z move with a hand near the emergency stop. Do this every time until
you have seen it work correctly on your machine, and keep doing it for any
print you would be upset to lose.
